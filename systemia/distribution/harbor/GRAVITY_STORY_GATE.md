# Harbor Gravity Story Gate | developer/operator contract

**Status:** tested offline proof-of-concept; **not connected to a live Harbor scheduler or Meta publisher**. Companion to [24/7 standing issue #2348](https://github.com/jgaethle10/forge-operator/issues/2348) and [editorial plan PR #2345](https://github.com/jgaethle10/forge-operator/pull/2345).

Use the fail-closed, no-network module `gravity-story-gate.mjs` before constructing a real Harbor Facebook publication job. Its primary purpose is to stop verified-but-misrouted news, unlicensed reuploads, fabricated Journal URLs, frozen Page dispatches, repeated story angles, and unsupported claims from reaching the separate operator-approved publication flow.

## Test

```sh
node --test systemia/distribution/harbor/gravity-story-gate.test.mjs
```

The assessment accepts a `evercraft.harbor.live-story.v1` story object (the staged schema from the current editorial operating order) and a trusted `context` built by existing owner-operated services:

- `context.approvedPages`: live provider identity readback, exact Page ID, approved/current names, ACTIVE status, founder approval, provider and approved beats.
- `context.review`: recorded independent fact/attribution/safety/media-rights checks. These **must come from trusted QA receipts**, not text asserted by an external reporter or generated by the posting model itself.
- `context.publishedKeys`: stable, persisted provider-published dedup keys for the story and Page. Fetch from trusted durable publication ledger, not from an input packet.
- `context.journal`: current exact live canonical URL readback and accepted editorial status. An approved host-shaped URL alone is not proof a Journal story exists.
- `context.providerPostId`, `context.publishedPostReceipt` and `context.publishedKeys`: actual original post ID, status `PUBLISHED`, provider Page ID, independent readback, approved post message/link SHA-256, and the persisted story/Page/angle/update dedup key. These are required for a later Journal comment even though the corresponding Page post is deliberately blocked as a duplicate.
- `context.commentAuthority` and `context.sentCommentKeys`: separately permitted comment action, approved hash of the exact final text and a durable dedup ledger for `providerPostId + live Journal URL`. Do not mix Page-post credentials with comment permissions or allow retries to spam duplicate comments.

A passing story assessment returns `READY_FOR_AUTHORIZED_OPERATOR_REVIEW` and a **staged** `facebook_job_candidate` object using the worker's existing `evercraft.harbor.facebook-page-job.v1` schema. A passing result does not grant approval or call the provider. A Journal article may be pending while a verified, source-linked breaking-news post proceeds; a first-comment candidate is separately withheld until the exact Journal URL, provider post and independent approval are proved.

A held assessment contains reason codes. Inputs must be checked again immediately before any provider publish. The previously proposed Facebook job worker itself remains in [PR #2255](https://github.com/jgaethle10/forge-operator/pull/2255) and needs its own code review, operator-supplied hash/Page approval, credential validation, idempotency, actual runner installation, live provider receipt and independent readback. **No connection to that unmerged PR is made here.**

## Next integration tasks

1. Read current provider identity registry and approval/beat configuration via trusted signed Systemia state. Do not hardcode the 22 Pages or treat a pending rename as complete.
2. Populate the story candidate from primary/source-attributed references, include actual `post.message`, `post.link`, provenance and `media_search` attempt. Independently verify claims, imagery rights and release safety.
3. Feed existing publication ledger dedup keys. Use one Page per release packet and record different substantive angles as separate story revisions.
4. Gate the candidate and keep HOLDs out of the publisher; require both the exact Facebook job approval and any separate comment approval. The gate only generates candidate bytes, not a signed publication.
5. After actual publication, independently read back post ID, permalink and text. Write the dedup key durably. If a relevant Journal article is approved and live, run a separately authorized, exact-provider-post comment job with its own receipt, and reconcile ambiguous attempts before retrying.
6. Run overnight watchdog, rights/identity rejection, provider outage, stale headline and wrong-Page tests before advertising an autonomous 24/7 system.

**Important security limit:** the gate does not authenticate source reports, prove licenses, contact providers, or read private credentials. It trusts the distinct operator-controlled context fields, so a model must never be able to forge those receipts. Strict separation between proposed content, approved source/review material and the external publisher remains mandatory. The primary Journal domain still needs independently verified live deployment; no Base44 or third-party runtime is introduced.

# Evercraft Payments ↔ Stripe Integration Audit
**Date:** 2026-11-05 (Pacific)  
**Scope:** Canonical GitHub source (`main`), source-only PR #1896, October merchant-reconciliation evidence, and operator-supplied NextGen public runtime receipt at 2026-11-05T22:33:21Z.  
**Evidence class:** Repository/source and public runtime. **Not** a live Stripe account, payouts, event log, bank transfer, or production-order audit. Stripe account access was not granted in this session; no customer charge or Stripe mutation was attempted.

## Executive conclusion

**The checkout problem and the revenue/accounting problem are different.**
1. Seven existing live-mode *Systemia Stripe Payment Links* are the actual previously validated checkout surface for their seven exact SKUs. Their public product pages link **directly** to Stripe. The checked-in catalog says `canonical_order_reconciliation=manual_not_automated`. A successful payment through one of these links does not automatically become an Evercraft Payments order or Systemia fulfillment job.
2. Native *Evercraft Payments → Raven Nexus → Stripe* is the declared architectural authority, but the independently observed owned Fabric production health says **both owned transport URLs are unconfigured**. Its native checkout is held.
3. PR #1896 adds a source-only candidate owned payment operations service and signed webhook refetch. It is **not deployed**. As written, it models new Checkout Sessions generated by the service; it **cannot ingest or reconcile the seven already-existing Stripe Payment Links**. It also calls Stripe directly from the proposed service, without an implemented Raven Nexus provider/credential boundary.
4. Consequently, more GET probes of the seven links do not address our missing **payment-receipt → canonical-order → delivery** pipeline.

## Intended architecture vs actual evidence

Intended (documented `systemia/payments/README.md`):
```
Product / buyer / approved agent
    → Evercraft Payments (canonical order, identity, price, consent, state)
    → Raven Nexus (credential/processor adapter boundary)
    → Stripe (settlement)
    → signed & refetched provider events
    → Evercraft Payments paid/reversed receipt
    → Systemia entitlement / Shipping / reviewed delivery
```

**Currently available seven-link commerce path:**
```
Public Evercraft Services page → buy.stripe.com Payment Link
    → Systemia Stripe merchant account
    → provider settlement
    → [not evidenced: automatic Evercraft Payments order import]
    → [manual provider receipt reconciliation and human fulfillment review]
```

**Currently held native path:**
```
Owned Fabric POST /api/offers/{slug}/checkout
    → purchase-intent / payment-ops URLs (both absent in observed live health)
    → 503 owned_evercraft_payments_unavailable / no buyer charge
```

**PR #1896, not production:**
```
Fabric owned request (auth wiring candidate)
    → loopback-only Payment Ops prototype
    → direct api.stripe.com Checkout Sessions
    → local append-only JSONL journal
    → provider session refetch + signed webhook candidate
    → 'paid' local entry, fulfillment still awaiting human review
```

## Findings, ranked by business impact

### P0: Existing Stripe receipts do not flow automatically to Evercraft Payments
**Evidence:** `public/mesh/checkout-ready/verified-links.json` explicitly says `canonical_order_reconciliation=manual_not_automated`, `payment_received_verified=false` (catalog snapshot only), and existing Systemia webhooks point to historical provider endpoints. `public/mesh/checkout-ready/index.html` places the original fixed links directly into customer-facing `href` elements, not through native order creation.

**Consequence:** Stripe might settle a payment without the owned Evercraft canonical order, agent job, support notification, refund state or delivery record appearing. It is unsafe to infer *zero* sales from *zero* Evercraft receipts, and equally unsafe to claim sales without Stripe evidence. **Actual Stripe purchases/charges/payouts remain unobserved here.**

**Fix:** Build one bounded read-only reconciliation ingestion **for the seven pre-existing plink IDs first**, using authenticated Stripe records. Mapping is exact account + payment_link_id + price_id + product_id + amount + currency. Correlate existing Checkout Session, PaymentIntent, charge/refund/dispute and event identifiers; dedupe by processor identity; create a canonical `external_hosted_payment_link` Evercraft order *only after independently verified paid settlement*, preserving timestamp and actual consent/scope. Send owner-only fulfillment-review alerts. Backfill historical settled transactions with an operator-reviewed ledger, not autonomous delivery.

### P0: Public native Fabric cannot create an owned checkout today
**Evidence:** NextGen v2 independent HTTPS GET of `/health` returned:
- `checkout_purchase_intent_configured=false`
- `checkout_direct_offer_ops_configured=false`
- `checkout_operational_state=held_owned_payment_endpoint_unconfigured`
- `checkout_provider_paid_verified=false`
- `deployment_receipt_bound=false`

In main `systemia/mcp/fabric-local-runtime.mjs` around lines 1255–1260, **both** owned endpoints are required before processing even a direct offer; otherwise HTTP 503. The public `/offers` page returns 200 regardless of purchase readiness.

**Fix:** Provision an approved owned backend and independently attested TLS ingress, authenticate Fabric to the payment services, and verify test-mode order/return behavior. Do **not** insert placeholder URLs or turn off hold flags just to make health green.

### P0: New candidate does not reconcile old hosted Payment Links
**Evidence:** PR #1896 `systemia/payments/owned-ops-service.mjs` only handles `create_checkout` and `verify_checkout` for a known `order_key`/stored `checkout_session_id`. Unknown sessions are rejected as `order_session_mismatch`. The existing seven hosted links use Stripe `plink_...` identifiers and their own `price_...` identifiers and do not create candidate journal orders.

**Fix:** Add *a separate historical/direct-link settlement importer* rather than rerouting existing working links through untested native checkout. This recovers order truth and a customer service pipeline without touching working checkout.

### P1: Raven Nexus is documented as the processor boundary, but no corresponding production payment adapter is evidenced
**Evidence:** `systemia/payments/payment-routing.mjs` declares `provider_boundary:'raven_nexus'`, while the PR's `stripeAdapter` invokes `https://api.stripe.com/v1/checkout/sessions` directly with a secret from `STRIPE_SECRET_KEY`. This is a candidate credential boundary, **not demonstrable Raven Nexus orchestration**.

**Fix:** Implement a narrow, replaceable Raven Nexus payment adapter/credential service and identity-scoped request signing before calling it the canonical route. Keep all keys, customer data and provider receipts outside public GitHub and chat.

### P1: Candidate backend is not yet connectable by existing Fabric config
**Evidence:** Main `systemia/mcp/owned-payment-transport.mjs` accepts approved first-party **HTTPS** URLs. PR #1896 `startOwnedPaymentServer` binds default `http://127.0.0.1`, and only implements `POST /api/payments/ops`. Main Fabric requires **two** URLs, including a legacy-shaped `purchase_intent` contract. HTTP loopback is not the public Fabric-approved origin.

**Fix:** Choose one authoritative owned payment service and provide the needed exact contracts over authenticated, private-network first-party TLS, or refactor Fabric to one proven contract without weakening validation. Keep native checkout held until the external route is independently demonstrated.

### P1: Stripe webhook, reversal and refund safety not production-grade
**Evidence:** PR #1896 `stripe-webhook-verifier.mjs` validates signature/timestamp then refetches the session before recording payment. This is a good source-level boundary but has **no durable event-id replay register, complete reversal/dispute ledger, queue/outbox, private webhook ingress deployment, or service receipt evidence**. Signed reversal events deliberately fail with 503.

**Fix:** Durable signed-event inbox indexed by account + Stripe event ID, replay and out-of-order handling, canonical payment/refund/dispute transitions, human escalation for reversals and delivery already underway, dead-letter/retry monitoring, backup/restore and replay tests. Do not publicly expose prototype webhook endpoint yet.

### P1: Product registries are not one canonical SKU universe
**Evidence:** `public/mesh/checkout-ready/verified-links.json` names seven hosted Systemia services and `plink_/price_` IDs. `systemia/mcp/public-payment-offers.mjs` lists 11 different owned native offer keys, including a held `signal-brief`. `systemia/forensiscope/commercial-offers.mjs` builds route **metadata** (`order_state='not_created'`) and cannot settle payment. No one-to-one mapping of the seven hosted SKUs into the prototype native registry was found in the inspected paths.

**Fix:** Normalize product/offer, processor account, fixed price, fulfillment contract, buyer scope and merchant legal owner into a single versioned registry. Recognize `hosted_legacy` and `owned_native` as two *source channels* under one Evercraft order system. Do not substitute same-price unrelated offers.

### P1: No evidenced automatic delivery or owner alert from hosted settlement
**Evidence:** Catalog explicitly says `fulfillment_authority='human_review'`; `systemia/payments/README.md` requires verified provider receipts before entitlement, while current hosted checkout pages explain manual reconciliation.

**Fix:** At the first verified Stripe paid event, emit one durable `paid_pending_scope_or_delivery_review` receipt, notify the responsible owner once, and create a non-executing Systemia fulfillment proposal. Only execute after scope/capacity and applicable permission checks.

### P2: Merchant/payout and actual sales reconciliation require owner-authorized Stripe account access
**Evidence:** Catalog names **Systemia** as the Stripe settlement account; repo source does not establish legal merchant identity, payout destination, settlement balances, charges, fees, refunds or historical revenue. The Stripe account connection was not available for this audit.

**Fix:** In Stripe itself, inspect account owner/legal entity, live/test distinction, webhook endpoint destinations, charges and balances, payment-link sessions, refunds/disputes, payouts and tax/accounting export. No claim of missing money, wrong bank, or zero sales is justified before that review.

## Execution sequence: make current payments useful first

1. **Do not touch or retest functioning hosted buyer URLs unnecessarily.** Freeze exact SKU manifest with its expected account/link/price/product IDs.
2. **Audit current provider payment and payout activity, read-only:** identify paid sessions, refunds, disputes and pending payouts for this account and these seven link IDs. Distinguish *no account access* from *no purchases*.
3. **Build a single read-only, duplicate-safe Stripe-to-Evercraft Payments reconciliation adapter** that imports provider-verified existing payments before any native route release.
4. **Connect receipts to owner notification, Systemia delivery queue and customer contact records, with human scope/capacity approval**. Show states: paid/unpaid/refunded/disputed/fulfillment-held/fulfilled, never infer paid from redirect.
5. **Then** finish native checkout behind Raven Nexus, audited secret custody, durable webhooks/reversals, and independent test-mode acceptance.
6. Only after signed public deployment, live-owner approval and buyer consent, release native payment paths. Do not automatically merge/release PR #1896 because its tests are green.

## Success criteria

A real buyer pays for a known SKU → Stripe records the authoritative charge and settlement state → Evercraft Payments records *one* matching canonical paid order with source/account evidence → owner receives one alert → Systemia can inspect a bounded fulfillment request → delivery and refunds remain linked to the same order. A dashboard should distinguish provider-received gross from fees, refunds, net paid, pending payout and bank-paid payout.

**Bottom line:** The seven Stripe links are not the project. The missing *settlement truth and fulfillment bridge* is the project.
